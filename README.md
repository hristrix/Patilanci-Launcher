# Patilanci Launcher

Electron + React + Tailwind CSS desktop launcher for `hushed-mongoose.shulker.com`, using CurseForge project **1746375** (Patilanci SMP). Includes Microsoft sign-in, offline profiles, live server counts and player samples, automatic Fabric pack installation and updates, download progress, Java path and memory settings.

Press Play to open the separate Patilanci Minecraft console automatically. Minecraft preparation runs in a background worker so the launcher and console remain responsive. The console shows preparation messages and live game output with timestamps, search, warning/error filters, Copy, Clear, and an Autoscroll toggle. Closing the console stops Minecraft or cancels a pending launch; if stopping fails, the console stays open so you can retry. Closing Minecraft leaves the console open with its final output. Up to the last 2,000 lines stay in memory until Clear or a new launch, and account tokens are redacted. Run `npm run test:console` after building to check the window with fixture game processes.

## Discord activity

Discord Rich Presence connects to the local Discord desktop app and shows whether the launcher is open, Minecraft is starting, or Patilanci SMP is running. The elapsed timer resets when Minecraft starts. Discord can be opened before or after the launcher; presence reconnects automatically and is cleared on launcher exit. Discord must allow activity sharing in its Activity Privacy settings. The public Application ID is configured in `electron/discord-config.cjs`; name that application **Patilanci** in the [Discord Developer Portal](https://discord.com/developers/applications) to display “Playing Patilanci.” Optionally upload a Rich Presence image and set its asset key in that same config file. No bot token, client secret, Discord sign-in, player names, or Minecraft credentials are sent by this integration.

## Versioning

Launcher versions use `MAJOR.MINOR.PATCH` independently of Minecraft and the modpack. Bug fixes and hotfixes increment patch, new compatible features increment minor, and breaking changes increment major. Documentation, formatting, and test-only changes do not require a bump. Apply one bump per completed batch, using the highest applicable level.

```sh
npm run version:patch  # Bug fix / hotfix: 1.0.0 -> 1.0.1
npm run version:minor  # New feature: 1.0.1 -> 1.1.0
npm run version:major  # Breaking change: 1.1.0 -> 2.0.0
```

`npm run version:hotfix` is an alias for the patch command. These commands synchronize `package.json` and `package-lock.json` without creating a commit or Git tag. Add matching release notes to `CHANGELOG.md`, run the checks appropriate to the change, and commit the version files with the implementation. Future coding work follows the repository's `AGENTS.md` versioning rules.

Installers and the launcher version display use the package version. When publishing a production release, use GitHub tag `v<version>` (for example, `v1.0.1`) with the installer and updater metadata built from that same version. Bumping a version does not publish a release.

Made by [Hristrix](https://hristrix.com). The launcher footer opens the creator website in your system default browser; installer finish pages include the same link.

## Renderer code structure

The renderer separates page composition, desktop operations, and presentation:

- `src/main.jsx` loads fonts and styles, then mounts the launcher or console.
- `src/App.jsx` selects pages and connects state and actions to components.
- `src/config.js` holds shared page descriptions, defaults, and the server address.
- `src/hooks/useLauncher.js` coordinates startup, desktop subscriptions, configuration, and named account/game/update actions. It returns `state` and `actions` to `App`.
- `src/hooks/useServerStatus.js` owns server polling and shares pending refresh requests. `useInstanceStorage.js` owns storage reads. `useOfflineProfile.js` owns PIN fields, validation, debounced profile lookup, and lockout refresh.
- `src/components/account/` contains the player card, offline form, launch controls, and launch progress. `AccountPanel` composes them and owns the skin dialog.
- `src/components/home/` contains `HomeHero`, which combines the animated world, Play controls, and account area, plus the dashboard cards. `HomeOverview` arranges them with the account panel.
- `src/components/layout/` contains the sidebar, page heading, alerts, and footer. Settings and community content live in `Preferences.jsx` and `PlayerPanel.jsx`.

Pass the desktop bridge as `api` from the entry point; components receive data and callbacks through props. Keep desktop requests in the coordinating hooks or existing feature components. Preserve DOM classes when moving markup because the responsive styles use those classes and their parent relationships. `npm run validate` exercises sign-in, PINs, launch states, updates, skins, and responsive layouts through the actual renderer.

## Run

Development requires Node.js 22+ and uses npm 10.9.4, matching GitHub builds. On Windows x64, the launcher installs the modpack's required Java runtime automatically; players do not need to install Java separately.

```sh
npx npm@10.9.4 ci
npm start
```

On PowerShell systems that block npm.ps1, use `npm.cmd` instead of `npm`.

Keep `package-lock.json` tracked. Run `npm run check:lockfile` before committing dependency changes; it rejects versionless optional-dependency stubs that can cause npm's `Invalid Version` error on clean installs. Use `npx npm@10.9.4 install` when updating dependencies. If the lockfile needs repair, regenerate it with npm 10.9.4 in a clean folder without an existing `node_modules` tree, then test a real `npm ci` installation there; a dry run alone does not catch this failure.

Before pushing launcher changes, run `npm run validate`. This checks the lockfile, synchronized versions and changelog, then runs unit tests, the renderer build and desktop/console checks. To exercise installer packaging locally, run `npm run dist:preview` as well. Pull requests and pushes to branches other than `master` run these checks and build a preview installer automatically; **Validate Windows installer** can also be started manually from Actions. Preview installers are saved as workflow artifacts and are not published as stable releases. Both workflows share Node 22 and npm 10.9.4 through `.github/actions/setup-launcher`.

Pushes to `master` build the production installer after validation, verify that the installer and `latest.yml` agree on the version, filename, size and SHA-512, save the release files as downloadable workflow artifacts, and only then publish the GitHub Release. Failed runs save available screenshots and builder diagnostics. Each stable release still needs a new launcher version and matching changelog entry; published versions are never overwritten. GitHub Actions must be enabled and `PUBLIC_DOWNLOAD_SERVICE_URL` must remain configured for production releases.

Closing the main launcher window stops Minecraft, cancels pending Java preparation, and exits the launcher completely. There is no system tray icon or background launcher after closing. Closing the game console still stops Minecraft; closing Minecraft still leaves its console open. `npm run test:exit` checks that closing waits for cleanup and exits all launcher windows.

Home and Modpack show the logical size of the installed Minecraft instance, including game assets, libraries, mods, maps, saves, and settings. Modpack lists managed Java separately and has **Refresh size**. The asynchronous scan has bounded filesystem concurrency, skips symbolic links, and caches results for one minute; backups and staged updates outside the active instance are excluded. Incomplete scans are labelled as a lower bound. Mod changes, pack activation, and Minecraft exit invalidate the size cache.

Repeat launches skip the redundant ownership scan of every mod JAR when the pack file ID is unchanged; mod management and actual updates still reconcile the inventory. Java preparation and the fresh latest-release verification run concurrently and must both succeed. The Minecraft worker caches successful SHA-1 verification in `patilanci-checksums.json`; an unchanged expected hash, size, modification/change timestamps, device and file identity allow reuse. Changed or missing files are checked again and the normal downloader repairs failed checks. A corrupt or missing verification cache triggers full verification. This also fixes the launch library's un-awaited library-checksum check. Pack updates reuse missing assets and libraries in staging, with incoming pack files taking priority; copies are independent so repairing a file cannot modify the previous instance. The game console reports launcher preparation time through Java process startup, not the time until Minecraft finishes loading mods or joins the server. No extra JVM tuning flags are added.

Java requirements come from the selected Minecraft version's official metadata and the installed loader profile. Java 8, 17, 21, and 25 are managed separately under `%APPDATA%/patilanci-launcher/runtimes`. On first Play, the matching Eclipse Temurin JRE is downloaded through the [Adoptium API](https://github.com/adoptium/api.adoptium.net/blob/main/docs/cookbook.adoc), checked against its SHA-256 checksum, extracted, and tested before activation. Later launches reuse it; cached Minecraft metadata allows Java selection without another network request. Download and extraction run in a background worker and can be cancelled by closing the game console. System Java installations and PATH are not modified.

In Settings → Java versions, automatically managed rows have disabled path fields. Browse chooses that version's `bin/java.exe` and enables its field for custom path editing. Reset clears the custom path and returns the row to disabled automatic management; click Save preferences to keep changes. Custom paths are checked before launch, and a mismatched version blocks launch with a message explaining how to fix it. Existing custom Java paths migrate to the corresponding version row. Automatic runtime downloads currently support Windows x64, matching the distributed installer.

If the Windows graphics driver causes the normal launcher process to exit during startup, use `npm run start:compat` to disable hardware acceleration. The 3D skin preview is also exercised in this mode by `npm run test:desktop -- --disable-gpu`; it falls back to an unavailable message if WebGL cannot initialize.

Player settings contain memory allocation and the Java path. Download credentials are managed outside the player UI. When an HTTPS download service is configured, new players fetch the latest pack through that service without receiving the CurseForge credential. When no service is configured, the developer installation can still use its previously provisioned encrypted local key with Electron safeStorage. Saving player preferences preserves that encrypted value, and the renderer cannot replace it. No key is hardcoded or included in this source. The configured public service URL is `https://patilanci.net/launcher`; the new Pages Function still needs its Cloudflare secret and deployment before downloads on a fresh player computer can work.

Microsoft sign-in opens the MSMC Microsoft authorization window and requires a Minecraft Java entitlement. Sessions are saved in `session.enc` beside launcher settings using Electron's operating-system encryption. The Microsoft refresh token stays in the main process, restores sign-in on restart, and renews expired Minecraft credentials before Play. A temporary restoration failure keeps the saved token for a later retry; revoked authorization requires signing in again. Offline profiles use a local username and work only if the server accepts offline clients. They do not bypass online-mode authentication or a whitelist.

Home personalizes the banner and sidebar with the active player's name. The sidebar displays the player's skin head with its overlay and uses the bundled Steve head when signed out or the skin is unavailable. A Microsoft account uses the Minecraft Java profile name and active skin returned by sign-in. Skin PNGs are fetched in the main process from the official `textures.minecraft.net` host with a size limit and returned as image data without tokens. The bundled `skinview3d` renderer supports classic and slim models in a fixed three-quarter pose. Dragging, camera controls, automatic rotation, and idle animation are disabled. It renders once after loading and redraws when resized, without a continuous animation loop. Signing out or leaving Home disposes of the renderer. A missing texture or unavailable WebGL shows a fallback message. Signed-in offline profiles resolve a public skin by nickname through Ely.by, which also proxies public Minecraft skins. These previews use the same static 3D renderer and remain labelled as offline profiles. Unauthenticated names trigger no skin requests. Unknown names keep the neutral voxel avatar. The banner also displays actual server counts and latency when available.

Signing in does not download Minecraft. On Play, both account types use the same instance at `%APPDATA%/patilanci-launcher/instances/patilanci`: the launcher prepares the required Java runtime, then the launcher core downloads missing Minecraft client files, assets, and libraries there before starting the game. Existing files are reused.

After sign-in, the account panel shows only the active account type. Sign out before switching between Microsoft and offline profiles or changing the offline name. Account changes are blocked while Minecraft is running. While the game runs, Play becomes **Stop Minecraft**; stopping targets the game process launched by this launcher (including its process tree on Windows). **Stopping…** remains disabled until that process exits, and closing the game normally also restores Play. Renderer reloads retain the running-game state.

Offline profiles require a local 6–12 digit PIN. First use asks for confirmation. Successful PIN verification saves that profile's session on this computer, so subsequent plays and launcher restarts do not require the PIN again. The last authenticated account mode and offline name are restored. Signing out clears saved sessions for both account types; the next offline sign-in requires the existing PIN. PINs themselves are never saved in the session. PINs use random salts and scrypt hashes with a constant-time comparison. Five incorrect attempts lock that profile for five minutes, including across launcher restarts. Profile names are matched without regard to case while preserving the original spelling used for the offline UUID. PIN records live in `offline-profiles.json` beside launcher settings, outside the instance, and contain no plaintext PINs. The renderer receives only protection status, and PINs are never sent to Minecraft or the server. Corrupt records block verification rather than resetting protection. Only one launcher instance runs at a time so concurrent windows cannot race PIN counters or installations. There is no automatic PIN reset in the UI. This protects casual use of this launcher on this computer; someone with control of local files or another launcher can bypass it. Server identity protection requires server-side authentication.

The launcher requires the newest published client pack on every Play, including beta or alpha releases when those are newer. The launcher requests one release from the hosted service, which compares all CurseForge file pages by publication date (then file ID when dates match) and returns only the newest client pack, excluding server packs. Direct developer API access performs that comparison locally. The selected manifest provides the exact Fabric loader and mod versions; individual mods are not independently upgraded beyond that manifest. The launcher checks again after installation, before preparing Minecraft. A failed check, unavailable newest file, or release published during installation blocks launching an older pack. There is no cached-version fallback or version selector. A valid API key and internet access are required for every launch. Verification reflects the CurseForge API response at the time of the check; an already running game is not interrupted when a new pack is published.

Startup opens a branded splash before Home. Its ordered checks are launcher updates, saved Microsoft/offline session restoration, and the newest CurseForge client pack. Microsoft refresh tokens are renewed automatically; a session that cannot be restored is retained and marked as needing sign-in on Home. Offline sessions are checked against the local PIN profile records without asking for an already verified PIN. No saved account is required to prepare the pack. The launcher automatically installs the pack on first use or downloads a changed release; matching file IDs skip downloads. Renderer reloads share the startup operation. Failed startup checks show Retry startup and Open launcher recovery actions. Play still requires a successful latest-pack check. Saves, settings, and personal mods retain the preservation rules described above.

## Set your skin

After signing in, click the shirt button beside your player name. Premium accounts have a **Minecraft account** tab: choose a PNG, preview it, select Classic or Slim, then **Apply to Minecraft account**. Supported images are 64 × 64 or legacy 64 × 32 (Classic only), up to 1 MB. Close Minecraft before uploading. The native file picker validates and decodes the image in the main process; only its preview and an opaque selection ID reach the renderer. The authenticated upload goes directly to Minecraft's account service. Rejoin or relaunch after a change. A server skin override may require `/skin reset` before the account skin appears.

The **Server skin** controls support the [SkinRestorer mod by Lionarius](https://www.curseforge.com/minecraft/mc-mods/skinrestorer), a separate project from the SkinsRestorer plugin. Both offline and premium profiles can choose a Minecraft username, an Ely.by username, or a public HTTPS PNG URL with Classic/Slim selection. Copy the generated command and run it in Minecraft chat after joining. For an offline player's own PNG, use **Open Ely.by skins**, upload and apply the skin to an Ely.by account, then use that account's name in the launcher. This can differ from the offline player name.

For signed-in offline profiles, **Save for launcher** remembers the source, value, and model and updates both the character preview and sidebar head. A validated PNG snapshot is kept per profile in `offline-skin-selections` under launcher user data, so the choice survives restarts and service outages. Reopen the dialog to restore the saved fields; save again to refresh a changed source. A failed save keeps the previous skin. Public PNG previews accept direct HTTPS URLs, refuse redirects and private/local destinations, and enforce the image size limit.

On Minecraft 1.21.10 launches, the launcher installs [CustomSkinLoader 14.28 for Fabric](https://modrinth.com/mod/customskinloader/version/2C8mIbK2), unmodified, directly from its official CDN. The exact size and SHA-512 are pinned in `electron/shared-skins.cjs`; verified bytes are cached under launcher user data in `skin-mods`. This mod is also installed for premium players so they can see shared offline skins. Existing server-provided textures take priority, including official premium skins and SkinRestorer overrides. An offline player's saved PNG is used for their own character when no server texture exists. Other players are looked up through Ely.by, then Mojang. No authentication service or Minecraft access token is replaced. The Mods page lists the installed client mods.

**Sharing across servers uses your in-game name.** Upload and apply your skin on an Ely.by account with exactly the same name as your offline player. Other players need an Ely.by-compatible skin loader, such as this launcher. Saving a different owner's skin or PNG locally does not publish a shared name mapping. You see that saved choice locally; users on unrelated clients will not automatically see it. Server-provided skins can take priority. No launcher can guarantee an offline skin is visible to every player on every server.

On Patilanci, the bundled [Skin Companion](companion/README.md) sends the saved own-player SkinRestorer command automatically for offline launches. It waits for the server command tree, then sends once after joining, with a bounded retry after a supported successful login/registration confirmation. It displays when a command is sent; SkinRestorer's own response confirms success or reports failure. The server must permit the command and chosen provider. Premium profiles send no automatic commands; commands are scoped to the configured Patilanci hostname and selected player. The copy buttons remain available for other servers, different authentication messages, or manual recovery. **Reset launcher skin** removes the saved preview/local override and automatic command; it does not delete the server's saved skin. Copy and run `/skin reset` to reset that separately. See the [SkinRestorer command reference](https://github.com/Suiranoil/SkinRestorer/wiki/Commands).

CustomSkinLoader configuration and local skin snapshots survive pack updates with the existing player-data preservation rules. The launcher preserves unrelated config fields and custom providers and keeps a first-edit backup of an existing config. Only its own provider entries are refreshed. Conflicting mod copies or invalid existing configuration stop preparation with an actionable error rather than replacing personal files. The integration currently targets Minecraft 1.21.10; review and update both client mods before changing the pack's Minecraft version.

`npm run validate` includes synthetic PNG upload, shared skin configuration/download verification, and SkinRestorer command tests, plus desktop checks of premium skin selection/application, offline commands, and compact dialog layout. Build the companion with `companion/gradlew.bat build` from its directory to compile against Fabric and run command scheduling checks. These checks do not upload real skins or contact a Minecraft server. Live account upload and multiplayer visibility still need testing with an account and the configured server.

## Launcher application updates

Installed production Windows NSIS builds use `electron-updater` with public GitHub Releases from [hristrix/Patilanci-Launcher](https://github.com/hristrix/Patilanci-Launcher), configured in `electron/launcher-release.cjs`. Release builds generate the GitHub update configuration and metadata automatically. Development runs, unsigned preview installers, and Store builds do not install NSIS updates.

The startup splash checks the launcher first. A newer published stable release downloads automatically, with progress. Once verified by the updater, choose **Restart and update**: a branded restart screen appears before the launcher closes, followed by a compact update status window while files are replaced. The setup wizard stays skipped. Patilanci then reopens automatically, acknowledges the update on the startup splash, and shows the running version in a dismissible confirmation on Home. Account/modpack preparation continues normally. Repeated clicks share one pending restart; if update preparation fails, the downloaded update remains available to retry. Installers also recognize the update flag sent by older launchers and skip the wizard for those upgrades. A manual first installation still uses normal setup. Updates never auto-install merely because the app quits. They cannot be installed while Minecraft or another launcher operation is running. Failed checks show a warning with retry and do not falsely report that the launcher is current. Settings also has a manual launcher update check.

While open, the launcher checks for launcher and modpack updates every minute and on window focus. Checks wait for startup and active launcher operations to finish, but can run while Minecraft is playing. In-app notices show launcher download progress, **Restart and update** when ready, and **Update modpack** for a new pack release. These actions wait until Minecraft closes. Notification banners dismiss automatically seven seconds after appearing, or immediately with their close button. Progress changes do not reset the timer; a newly ready update gets its own seven seconds. Dismissal hides that notice for the current session; Settings and Modpack retain their update actions. These are periodic checks, not server push notifications. Pack updates are applied only by the update action, startup, or Play, preserving player files as described above. Temporary service failures are retried automatically without discarding a known available pack update.

For each production release:

1. Set the deployed public modpack download-service URL. Code signing is optional; without certificate configuration, the production installer is unsigned.
2. Increment `package.json` and `package-lock.json` to the next semantic version.
3. Run `npm run dist`. The build prepares files locally and does not publish them.
4. Create a non-draft, non-prerelease GitHub Release with a matching tag, for example `v1.0.1`, and attach the generated setup executable, `latest.yml`, and any generated `.blockmap` files from `release/production/installer/`.
5. Publish the release after all of its assets have finished uploading. Keep older releases available for existing installations.

The repository must be publicly accessible for credential-free client update checks. No GitHub token is shipped to players. An update becomes available after the production assets are published, either by the master release workflow below or the manual process above. A real installed-version upgrade still needs testing from an older installed version. The public download service remains required.

Downloads are SHA-1 verified when CurseForge supplies that hash. Updates stage separately and preserve existing player files and folders, including saves, screenshots, resource packs, shader packs, options and keybindings, server lists, mod configuration, Xaero maps and waypoints (including newer locations), and other mod settings outside `config`. Existing player files take precedence over pack defaults; newly introduced files are retained. Only launcher-managed paths are excluded from this copy: `mods` (handled separately by the ownership inventory), `versions`, `libraries`, `assets`, `natives`, `runtime`, `runtimes`, `.fabric`, `.quilt`, `.cache`, `.mixin.out`, `logs`, `crash-reports`, `patilanci-install.json`, and `patilanci-mods.json`. The update activates with a backup of the previous instance. A file/folder conflict blocks activation and leaves the original instance intact. The backup is for recovery and is never a launch target. Files disabled for third-party download stop installation with an error.

Player counts come from direct Java server status queries with SRV support, refreshed every 30 seconds. Names are only those exposed in the server sample; vanilla status does not guarantee a complete roster. A complete list requires a server-side plugin/API.

## Manage mods

The Mods page has **Patilanci mods** and **My mods** tabs with search, versions, and filenames. Install the pack first, then choose **Add mods** to import one or more downloaded Fabric `.jar` files through the native file picker. JAR metadata is checked for Fabric support and duplicate mod IDs, aliases, and filenames. Imports are limited to 128 MB per JAR. Use mods and dependencies compatible with the pack's Minecraft version; the launcher does not download additional dependencies or guarantee compatibility for player additions.

The main process records ownership in `patilanci-mods.json`. Pack-provided files (including override JARs), existing files from older launcher installations, and untracked files are protected. Only files recorded as player additions receive a Remove action, and backend removal checks enforce the same rule. Imports cannot overwrite existing files or replace a bundled mod under another filename. Add/remove operations are blocked while Minecraft or an installation is running. Removal deletes the instance copy and leaves the original imported download intact.

Personal additions and their ownership records are carried into staged pack updates. Manually copied JARs added after the ownership inventory was created also survive repeated updates and remain protected from launcher removal. If a personal JAR was changed outside the launcher, its current contents and metadata are preserved. If a new required mod conflicts with an addition, the update stops before activation and asks the player to remove that addition through the Mods tab or instance folder. If an identical addition becomes part of a new pack, it becomes protected. The latest-version launch requirement still applies.

## Build a Windows installer

### Automatic GitHub Releases

`.github/workflows/release.yml` runs only on pushes to `master`. Pushes to other branches, pull requests, and tag pushes do not build or publish installers. Develop on feature or hotfix branches, update the version and changelog, then merge into `master` to release.

Before the first release, configure the repository under **Settings > Secrets and variables > Actions**:

| Type     | Name                          | Value                                                                                                  |
| -------- | ----------------------------- | ------------------------------------------------------------------------------------------------------ |
| Variable | `PUBLIC_DOWNLOAD_SERVICE_URL` | Deployed HTTPS URL of the public modpack download service. CI embeds this public URL in the installer. |
| Secret   | `CSC_LINK`                    | Base64-encoded Windows code-signing PFX certificate, as supported by electron-builder.                 |
| Secret   | `CSC_KEY_PASSWORD`            | Password for that signing certificate.                                                                 |

The workflow uses GitHub's automatic `GITHUB_TOKEN` with `contents: write` permission to publish; no personal access token or CurseForge credential is needed in the workflow. Repository or organization policies must permit that permission.

Each `master` push validates the version and release notes, installs locked dependencies, runs unit and desktop checks on Windows, and builds the production NSIS installer. Only `PUBLIC_DOWNLOAD_SERVICE_URL` is required; the certificate secrets in the table are optional. Without `CSC_LINK`, the workflow builds an unsigned production installer. It creates a draft release tagged `v<version>` at the pushed commit, uploads `Patilanci-Launcher-Setup-<version>-x64.exe`, `latest.yml`, and any blockmaps, then publishes it as the latest stable release. Download the installer from the repository's **Releases** section. Existing installed production launchers use the same metadata to detect updates.

Published versions cannot be overwritten: increment the version and add changelog notes before another release. A failed upload leaves the release as a draft; rerunning the same commit resumes it. A draft belonging to a different commit requires a new version or removal of that abandoned draft. Missing service configuration fails with an actionable error. When signing credentials are explicitly supplied, signing and signature verification must succeed.

### Local builds

Run `npm run dist` to build an unsigned production installer without a certificate. It retains the normal app identity, automatic updates, and public download service. Windows may display an unknown-publisher or SmartScreen prompt for an unsigned installer.

If you later choose to sign builds, configure `CSC_LINK` (or locally `WIN_CSC_LINK`) with the signing PFX and `CSC_KEY_PASSWORD` with its password. For GitHub Actions, use the optional `CSC_LINK` and `CSC_KEY_PASSWORD` secrets. Certificate auto-discovery is disabled when no certificate is explicitly configured.

Set the deployed public modpack service URL in `electron/download-service-config.cjs` for a local production build, or use the `PUBLIC_DOWNLOAD_SERVICE_URL` repository variable for the release workflow. Only explicitly signed builds verify Windows trust, timestamps, and matching launcher/installer publishers before reporting success. Unsigned builds skip those certificate checks.

```sh
npm run dist
```

For a separate preview installer intended for local testing, run `npm run dist:preview`. Its setup executable is written under `release/preview/installer/` with PREVIEW in its filename. Preview builds include the latest launcher code but still need download-service configuration to install the modpack on a fresh computer; production builds use `npm run dist` even when unsigned.

The Windows setup wizard includes a branded welcome page, installation scope and folder selection, progress, and a finish page with an option to open the launcher. It creates desktop and Start menu shortcuts. Reinstalling or uninstalling keeps launcher settings, saved sessions, profiles, Minecraft instance data, and managed runtimes in the user's application-data folder. The installer does not bundle Java or the modpack; the launcher downloads them when needed on Play.

Application and installer icons are generated from `public/brand/patilanci-monogram.svg`. `npm run build:artwork` refreshes the transparent window PNG and all sizes in the Windows ICO; installer builds run this step automatically. Windows uses the same `com.patilanci.launcher` identity as the installed shortcuts. Updates notify the Windows shell to refresh the executable and shortcut icons. Existing taskbar pins are preserved; a pin still showing a cached old icon may need to be unpinned and pinned again after updating.

Installer output is in `release/`. `npm run dist` first checks that a public download service URL is set so a player build cannot accidentally depend on the developer computer's saved key. Browser-only UI preview: `npm run dev`; game and account features require Electron. `npm test` checks archive paths, settings, PIN protection, release selection, profile filtering, and the download service; `npm run build` checks the renderer build. Real Microsoft authentication, API-key downloads, Java launch and joining require valid credentials and server access and must be exercised before distribution.

`npm run test:desktop` checks all five pages, mod import/removal and protection, account mode switching, logo loading, horizontal overflow, and Play button visibility at desktop and compact sizes in a hidden Electron renderer. It also runs the real WebGL skin renderer with a synthetic PNG and Microsoft profile fixture, checks signed-in Home at four sizes, and verifies signed-in offline skin previews, unsigned-profile privacy, and the missing-skin fallback. Screenshots are saved in `artifacts/`. Tests use an offline status fixture and temporary synthetic mod JARs, simulate the file picker selection, and do not access accounts, real instances, or download game files. Some moderate advisories remain in legacy transitive dependencies of the Minecraft library and build tools; review those before public distribution. Patched ZIP and multipart dependencies are pinned through overrides.

The interface uses the supplied Patilanci SMP logo and the existing website palette: near-black `#0b0b0d`, cream `#f4e7cf`, red `#e53935`, and gold `#f2b632`. Manrope and Oswald are bundled locally so the interface works without an external font service. Brand assets live in `public/brand/`, and the voxel landscape is a native SVG React component in `src/components/WorldScene.jsx`.

Button treatments are shared in `src/controls.css`: red gradients for primary actions, warm gold-bordered secondary and icon controls, matching selected tabs, and a darker red treatment for removals. Hover, pressed, disabled, and keyboard-focus styles apply across pages; page styles only arrange these controls.

## Download service for new players

The Cloudflare Pages download service is maintained in the separate Patilanci Landing Page repository. See that repository's `CLOUDFLARE-SETUP.md` for deployment instructions. Its streaming Pages Function serves `https://patilanci.net/launcher` alongside the existing coming-soon page. Configure the encrypted `PATILANCI_CURSEFORGE_KEY` Pages secret and deploy that site's changes before distributing the launcher. The configured URL alone does not establish that the service is live. Set the launcher repository's GitHub Actions variable `PUBLIC_DOWNLOAD_SERVICE_URL` to that same URL.

The prepared Node service is `server/download-service.cjs`. Deploy it on your own server behind HTTPS and set these environment variables there:

```text
PATILANCI_CURSEFORGE_KEY=<the working CurseForge key, on the server only>
PUBLIC_DOWNLOAD_URL=https://downloads.your-domain.example/launcher
PORT=8787
```

The example address is a placeholder, not a deployed service. Start with `npm run start:download-service`. It listens on `127.0.0.1:8787`; the HTTPS reverse proxy must preserve the `/launcher` path prefix. A GET to `/launcher/health` returns service status. Keep the environment variables on the server; they are not part of an installer.

Set `PUBLIC_DOWNLOAD_SERVICE_URL` in `electron/download-service-config.cjs` to the real public HTTPS base URL before running `npm run dist`. For local development, `PATILANCI_DOWNLOAD_SERVICE_URL` can override it. The service exposes only the Patilanci release list and files referenced by the latest client manifest; it is not a general CurseForge proxy. It validates pagination, blocks unrelated files, rewrites metadata download URLs to its own streaming endpoints, and sends the API key only to CurseForge API/CDN hosts. No credentials appear in responses or download URLs. It refreshes the manifest allowlist after a minute or when a newly published pack ID is requested.

Offline skin lookup follows [Ely.by’s documented skin service](https://docs.ely.by/en/skins-system.html), used by [Legacy Launcher’s Ely.by integration](https://ely.by/load/). Requests contain only the chosen nickname, never Microsoft tokens or local PINs. The main process limits metadata and PNG sizes, accepts only approved Ely.by storage or official Minecraft texture paths over HTTPS, and refuses redirects. Public skin images are cached outside the Minecraft instance in offline-skin-cache for ten minutes, with up to seven days of cached fallback during outages; missing names and failures are retried after one minute. This changes the launcher preview only. The skin seen by other players still depends on the server or client skin system; [SkinsRestorer](https://skinsrestorer.net/docs/installation/quick-start) is a server-side option. A nickname lookup does not verify account ownership and cannot discover skins stored privately by another launcher or a server-specific plugin.
